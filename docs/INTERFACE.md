# Fair Chance coin interface (1.0.0-rc.7)

Status: Frozen as 1.0.0-rc on 2026-11-12. The paper test set 1.0.0-rc.3. It becomes `1.0.0` when every coin rule in this file passes its sandbox tests. There is no vault, so penalties and the pool part of fees stay in locked liquidity.
`1.0.0-rc.2` (builder, 2026-11-12): `cap_used` counts only the part of a band sell above the account's first allowance in the window. Also in `1.0.0-rc.2`: `FC_EARLY_WINDOW`, and the creator fee share (ADR 0010): new fields, one new view, one claim method, one new event, two refusal codes. All are additions; no existing field changes meaning except that `real_near` and `real_near_now` now exclude the creator balance.
`1.0.0-rc.3` (builder, 2026-11-12 and 2026-11-13): the c cap is checked against real NEAR after each sell, so `cap_total` and `cap_left` change meaning; the creator fee depth test uses the lowest real NEAR of each 1 h window; `FC_TRANSFER_CALL_NOT_POOL` is renamed `FC_TRANSFER_CALL`; new refusal codes `FC_SEND_TO_COIN` and `FC_RECEIVER_WOULD_BE_LARGE`; new field `fc_account.max_receive`; every large, band and marked sell is checked, also when its own net adds zero; marked sells count net of the same account's buys for the cap only (the marked allowance stays gross); an account's buys first offset its sells that do not count (small sells and a band account's first allowance), and each account's signed value is clamped at zero when read, before it is added to the cap total; window 0 starts its lowest real NEAR at 0, and a claim needs at least 24 h since `depth_ok_since`.
`1.0.0-rc.4` (builder, 2026-11-13): additions only. New `fc_pool` fields `large_holders` and `creator_group_share_bps`. `FC_ONE_YOCTO` now also lists `claim_creator_fees`, which already needed 1 yoctoNEAR. Standard methods are named under Conventions.
`1.0.0-rc.5` (builder, 2026-11-13): additions, and the class change and the two unregister changes at the end of this line. The buy and sell methods are named: `buy(min_tokens_out)` and `sell(amount, min_near_out)`. `sell` takes `min_near_out` for all of `amount` and checks it per token. New `fc_rules` field `description`. `new` refuses any caller that is not the coin's parent account, and any icon that is not a WebP data URL under 8 KB. New `fc_launch` field `description`; `fc_launch.launch_block` is the block of the coin's `new` (the factory reads it from the coin). `new` is payable: the attached NEAR is the creator's opening buy. `buy` from an account with no storage record is refused with the NEP-145 text. New refusal code `FC_UNREGISTER_WINDOW_OPEN`. Three changes, not additions: `class` (in `fc_account`, `fc_sell`, `fc_buy.class_after` and every class rule) is the window class with the class floor, not the live-balance class alone; a force-unregister at zero tokens with used allowance or a cap record in the current window now returns `FC_UNREGISTER_WINDOW_OPEN` (it returned `FC_UNREGISTER_WITH_BALANCE`), and a plain unregister while the account holds tokens now returns `FC_UNREGISTER_WITH_BALANCE` (it returned the standard NEP-145 error).
`1.0.0-rc.6` (builder, 2026-11-13): `cap_used` and `cap_left` change meaning. Marked sells count gross: a buy never offsets them. Tokens an account bought in the current window count toward the cap when it sells them, for every class, small too (ADR 0005); for the count a sell takes its marked part first, then the tokens bought in the window, then the tokens held from before the window. Each account keeps two counts per window: its marked NEAR out (gross) and one net of its other counted sells minus its buys; a buy no longer offsets the account's uncounted sells first. A small sell of tokens bought in the window fills as far as it passes the cap check or adds nothing to the cap used. `fc_account.unmarked.floor_left` also subtracts the marked tokens the account sold in the window (one floor per account per window). New `fc_early_window` fields `shared_allowance_used`, `shared_allowance_left` and `window_end_ns`. `penalty_applies_above` >= `max_full_fill_now` for a band account that holds marked tokens (equal with no marked tokens).
`1.0.0-rc.7` (builder, 2026-11-13): `fc_rules.creator_fee_share_bps` is the creator share the coin applies (in rc.6 it reported the planned 3000 while the coin applied 0); the coin now applies 3000. `new` is refused when the coin's balance minus its real NEAR and its creator fee balance does not cover its storage (in rc.6: minus its real NEAR only).
Builder-confirmed fields (2026-11-12): `fc_send.to_marked_amount`, `fc_sell.marked_sold` and `fc_account.in_creator_group`. They are outputs only; no rule reads them.
Change rule: a later change adds fields only, or bumps the version. Each change goes in a message to Kalu.

Consumers: the builder's frontend (coin page, receipts), any indexer, and any later replay of Fair Chance testnet coins. Kalu's issues #1 and #2 read public chain data and the rule text in each issue only; they do not call these methods.

## Conventions

- NEP-297 standard name: `fair_chance`. Version string: `1.0.0-rc.6`.
- Standard methods follow their NEPs and are not repeated here: NEP-141 (`ft_transfer`, `ft_transfer_call`, `ft_balance_of`, `ft_total_supply`, with NEP-297 `nep141` events `ft_mint` and `ft_transfer`), NEP-145 storage, NEP-148 `ft_metadata`, and NEP-330 `contract_source_metadata`.
- Every token or NEAR amount is a decimal string in the smallest unit (token base units, yoctoNEAR).
- Every time is a block timestamp in nanoseconds, as a decimal string. Block heights are numbers.
- Shares and rates are basis points (1 bp = 0.01%), as numbers.
- `class` is one of `small`, `band`, `large`. Class uses the live balance at each action, raised to the class floor of the window: never below the class just before the account's first action in the current 1 h window, and `band` at most from the floor. An account stays `large` until its balance is zero. Marked tokens show through `marked_balance` and `marked_tokens` fields, not through `class`.
- Marked tokens leave first on a send. A sell fills the marked part first, up to the account's pro-rata share, then the unmarked part, up to the account's own allowance.
- The coin also emits the standard NEP-141 events (`ft_mint` at launch, `ft_transfer` for sends, and for the token side of buys and sells, with the coin account as the other party).

## Windows

- One fixed grid from the launch time: window k runs from launch + k x length to launch + (k + 1) x length. Lengths: 1 h for unmarked accounts and for the pool-wide c cap, 24 h for early supply.
- Marked payouts count in the same 1 h cap window, gross (no buy offsets them), for the cap only.
- The token reserve for the 2% price cap is recorded at the first action in each window, before that action takes effect.
- In window 0, marked sells have no allowance in blocks 0 to N. Early-supply shares and the window-0 token reserve for early supply are recorded at the first action after block N.
- Known limit: every allowance and the cap reset at the same moment, so bots race at the reset.
- Depth for the creator fee claim: the contract keeps the lowest real NEAR of each 1 h window, updated at every action. A new window starts that value at the real NEAR carried from the last action. A window with no actions keeps that carried value. The lowest value is read after each action. A claim tests the last 24 full windows and the current window up to the claim. The claim does not change real NEAR. Window 0 starts its lowest value at 0 real NEAR. The contract keeps `depth_ok_since`: set by the first window whose lowest value is at or above the minimum, and cleared by any window below it. A claim needs at least 24 h since `depth_ok_since`.

## Refusals

- Hard refusals panic with a fixed error code. No `fair_chance` event is emitted, because a failed receipt rolls back and event indexers read successful receipts. Codes:
  - `FC_LARGE_CANNOT_SEND`: a large account sends.
  - `FC_RECEIVER_WOULD_BE_LARGE`: a send that would take a receiver that is not large to `large_threshold_bps` of supply or more. The message starts with the code and then gives the largest amount the sender can send. Added for `1.0.0-rc.3`.
  - `FC_TRANSFER_CALL`: `ft_transfer_call` to any receiver. Renamed from `FC_TRANSFER_CALL_NOT_POOL` in `1.0.0-rc.3`.
  - `FC_SEND_TO_COIN`: a plain `ft_transfer` to the coin account. Sells use only the sell method. Added for `1.0.0-rc.3`.
  - A send to yourself is refused with the standard NEP-141 error.
  - `FC_UNREGISTER_WITH_BALANCE`: `storage_unregister`, with or without force, while the account holds tokens. It replaces the standard NEP-145 error for a plain unregister with tokens.
  - `FC_UNREGISTER_WINDOW_OPEN`: `storage_unregister`, with or without force, at zero tokens while the account has used allowance or a real NEAR cap record (a buy or a sell) in the current 1 h window. Unregister is allowed again when the window ends, so the storage deposit is never locked. Added for `1.0.0-rc.5`.
  - `FC_CREATOR_CAP`: a buy by the creator group, or a send into the creator group, that takes the group above 4% of supply.
  - `FC_ONE_YOCTO`: a sell or a `claim_creator_fees` call without exactly 1 yoctoNEAR attached.
  - `FC_SLIPPAGE`: the price per token of the filled part is below the seller's minimum. Slippage is checked on the price per token, not on total NEAR out, so a partial fill does not fail slippage. From `1.0.0-rc.2` it also covers buys: a buy whose `tokens_out` is below the buyer's `min_tokens_out`.
  - `FC_EARLY_WINDOW`: a sell of marked tokens in blocks 0 to N. Added for `1.0.0-rc.2`.
  - `FC_NOT_CREATOR`: `claim_creator_fees` called by any account but the creator. Added for `1.0.0-rc.2`.
  - `FC_CLAIM_NOT_READY`: `claim_creator_fees` before the lowest real NEAR of every 1 h window in the last `claim_depth_hold_s` has been at least `claim_min_real_near`, or with a zero balance. Added for `1.0.0-rc.2`.
- A sell above a limit never panics for the limit. It fills in part, or fills zero, and emits `fc_sell` with the reason.

## View methods

1. `fc_rules()`: the fixed values of this coin.
   `creator`, `launch_block`, `launch_ns`, `p_bps` (200), `window_unmarked_s` (3600), `window_early_s` (86400), `early_blocks` (N), `large_threshold_bps` (T), `creator_cap_bps` (400), `real_cap_c_bps` (500), `floor_bps` (10), `penalty_bps` (1000), `virtual_near` (P), `swap_fee_bps`, `early_fee_start_bps`, `brake_drop_bps` (null = off), `creator_fee_share_bps` (s, the applied share of the normal swap fee `swap_fee_bps` that goes to the creator balance; never applied to `penalty_bps` or to the early-fee extra above `swap_fee_bps`), `claim_min_real_near` (X), `claim_depth_hold_s` (86400), `unclaimed_to_pool_s` (D, null = off), `code_hash`, `description` (the creator's one-line launch description; null when none was given; added for `1.0.0-rc.5`).
2. `fc_pool()`: `token_reserve`, `near_reserve`, `virtual_near`, `real_near`, `creator_fee_balance`, `large_holders` (number of accounts whose class is `large` now), `creator_group_share_bps` (creator group balance ÷ total supply, in basis points), `block`. Both new fields are added for `1.0.0-rc.4`. `real_near` is NEAR in the pool paid in by buyers, minus NEAR paid out. It never includes `creator_fee_balance`.
3. `fc_early_window()`: `early_blocks`, `blocks_left` (blocks of the early window still open, the current block included: N + 1 at block 0 after the launch, 1 at block N, 0 from block N + 1), `early_supply_total`, `shared_allowance`, `rate_per_token`, `buy_fee_bps_now`, `fee_end_block`, `shared_allowance_used` (marked tokens sold in the current 24 h window, all accounts together), `shared_allowance_left` (`shared_allowance` minus `shared_allowance_used`, at least 0), `window_end_ns` (end of the current 24 h window, when the shared allowance refills).
4. `fc_cap()`: the pool-wide real NEAR cap in the current 1 h window.
   `window_start_ns`, `window_end_ns` (the reset time), `real_near_now` (same definition as `fc_pool.real_near`, without the creator balance), `cap_total` (c x real NEAR now, before any further sell), `cap_used` (per account per window: the NEAR out of its marked sells, gross, never offset by a buy, plus its net of other counted sell payouts minus buys, from one signed running value that is clamped at zero when read, before it is added to the total (one account's buys never offset another account's sells, and each buy offsets once), with each buy counted as the full NEAR paid, fee included; for the count, a sell takes its marked part first, then the tokens the account bought in the window, then the tokens it held from before the window; the marked part and the bought tokens always count; of the tokens held from before, a large account's count, a band account's first allowance does not, and a small account's never count), `cap_left` (the largest NEAR out that one more limited sell can take now, checked against the real NEAR left after that sell: (cap_total minus cap_used minus c x the creator share of that sell) ÷ (1 + c), at least 0; the creator share grows with the sell size, so the spec solves it as one linear term), `is_full`, `fills_this_window`.
5. `fc_account(account_id)`: one holder's state.
   `class`, `balance`, `marked_balance`, `unmarked_balance`, `is_large`, `can_send`, `in_creator_group`, `max_receive` (largest amount a send to this account can carry now without taking it to `large_threshold_bps`; null for a large account; added for `1.0.0-rc.3`),
   `unmarked`: `allowance`, `used`, `left`, `floor_left`, `window_end_ns`, (`used` is net tokens in the window: max(0, tokens sold minus tokens bought); a buy gives room back, a sell first must fit when it happens),
   `marked`: `share_bps`, `allowance`, `used`, `left`, `floor_left`, `window_end_ns` (allowance 0 in blocks 0 to N),
   `max_full_fill_now` (largest sell that fills fully now with no penalty), `penalty_applies_above` (band only, else null; equal to `max_full_fill_now` for an account with no marked tokens, and at least `max_full_fill_now` for one that holds marked tokens, because the cap can hold back the marked part, which fills first).
6. `fc_quote_sell(account_id, amount)`: a preview of one sell now, with no state change.
   `tokens_filled`, `near_out`, `penalty_near`, `fill` (`full`, `partial`, `none`), `limit_reason` (null, `allowance`, `cap_full`, `floor`), `cap_left_after`.
   `limit_reason`: null when the whole amount fills; `allowance` when the sell fills up to the allowance left; `floor` when a large sell, or the marked part of a sell, fills only its floor (the part that fills at any cap) and the cap stops the rest; `cap_full` when the cap stops the sell at any other point. `fc_sell` uses the same values.
7. `fc_creator_fees()`: `creator`, `balance` (unclaimed), `claimed_total`, `depth_ok_since_ns` (null when the lowest real NEAR of the current window is below X), `claimable_now`, `claimable_at_ns` (earliest claim time if real NEAR stays at least X; null when not counting).
8. `fc_quote_buy(account_id, near_in)`: a preview of one buy now, with no state change. Added for `1.0.0-rc.2`.
   `tokens_out`, `fee_near`, `creator_fee_near`, `marked_tokens` (all of `tokens_out` in blocks 0 to N or for a creator-group buyer, else 0), `class_after`, `becomes_large` (true when the account is not large now and the buy takes its balance to `large_threshold_bps` of supply or more), `allowance_after` (the account's unmarked allowance in the current window after the buy). The frontend sets the buy's `min_tokens_out` from `tokens_out`.

## Change methods added or changed in 1.0.0-rc.2, 1.0.0-rc.3 and 1.0.0-rc.5

- `new(creator, name, symbol, icon, description, code_hash)`: the one-time start of the coin. Only the coin's parent account (the factory) can call it; any other caller is refused. The factory passes its one recorded `code_hash`. `icon` is null or a WebP data URL (`data:image/webp;base64,...`) under 8192 bytes; any other icon is refused. Caller and icon checks added for `1.0.0-rc.5`. `new` is payable: any attached NEAR is the creator's opening buy, run as one `buy` for the creator at the launch block under the same rules (it logs `fc_buy`). The factory attaches it from the `launch` argument `opening_buy`. `new` is refused when the coin's balance minus its real NEAR and its creator fee balance does not cover its storage, so the storage never comes out of the pool or the creator balance. Added for `1.0.0-rc.5`.

- `buy(min_tokens_out)`: payable; the attached NEAR is `near_in`. Takes `min_tokens_out` (token base units). The contract refuses a buy with `FC_SLIPPAGE` when `tokens_out` would be below it. The frontend sets it from the buy preview minus a small margin. A buy is never filled in part. A buy from an account with no storage record is refused with the NEP-145 text `The account is not registered: <account>`, before any state change, so the attached NEAR is returned. The buyer calls `storage_deposit` first (amount from `storage_balance_bounds`); a wallet can send `storage_deposit` and `buy` as two function-call actions in one transaction. Method name and the storage refusal added for `1.0.0-rc.5`.

- `sell(amount, min_near_out)`: exactly 1 yoctoNEAR attached, else `FC_ONE_YOCTO`. `amount` is the tokens asked (token base units). `min_near_out` is the NEAR the seller accepts for all of `amount`. The check is on the price per token of the filled part: the sell is refused with `FC_SLIPPAGE` when `near_out × amount < min_near_out × tokens_sold`. Method name and arguments added for `1.0.0-rc.5`.

- `claim_creator_fees()`: creator only, 1 yoctoNEAR attached. Sets the balance to 0, sends the whole amount to the creator, and checks the result in a callback. If the transfer fails (for example, the creator account no longer exists), the callback adds the amount back to `creator_fee_balance`, so no NEAR is lost between counters. `fc_creator_claim` is emitted in the callback, only after the transfer succeeds. Refusals: `FC_NOT_CREATOR`, `FC_CLAIM_NOT_READY`.

## Events (`fair_chance`, data is a list of one object)

1. `fc_buy`: `account`, `near_in`, `fee_near` (the whole swap fee, as before), `creator_fee_near` (s x the normal swap fee on `near_in`; the early-fee extra and the rest of the fee stay in the pool), `tokens_out`, `marked_tokens` (tokens marked by this buy: all of them in blocks 0 to N or for a creator-group buyer at any time, else 0), `class_after`, `block`.
2. `fc_sell`: `account`, `class`, `tokens_asked`, `tokens_sold`, `marked_sold`, `near_out`, `fee_near` (the whole swap fee on this sell), `creator_fee_near` (s x the normal swap fee on this sell), `penalty_near` (100% stays in the pool; no creator share), `fill`, `limit_reason`, `allowance_used`, `allowance_left`, `cap_used`, `cap_left`, `window_end_ns`.
3. `fc_send`: `from`, `to`, `amount`, `marked_amount` (marked tokens that leave the sender; marked tokens leave first), `to_marked_amount` (tokens marked at the receiver: equal to `amount` when the receiver is in the creator group, else equal to `marked_amount`). It covers creator-group receives that become marked.
4. `fc_cap_filled`: emitted each time the cap goes from "has room" to "full" (`cap_used` equal to or more than c x the real NEAR left after the sell). `window_start_ns`, `window_end_ns` (reset time), `real_near`, `cap_total`, `cap_used`, `by_account` (the sell that filled it), `fill_index` (1, 2, ... in the window).
5. `fc_became_large`: `account`, `balance`, `large_threshold`. Emitted by the buy that crosses T. The account cannot send from now until its balance is zero.
6. `fc_creator_claim`: `creator`, `amount`, `depth_ok_since_ns`, `block`. Emitted only after the payout transfer succeeds. Added for `1.0.0-rc.2`.
7. `fc_creator_fees_to_pool`: `amount`, `block`. Only if `unclaimed_to_pool_s` is set; emitted at the first action of a new window. Added for `1.0.0-rc.2`.

Factory event (`fair_chance_factory`): `fc_launch`: `coin`, `creator`, `code_hash`, `launch_block` (the block of the coin's `new`, equal to `fc_rules.launch_block`), `description` (as in `fc_rules`; added for `1.0.0-rc.5`). The factory emits it only after the launch batch succeeds.

## Paper test, cases 3 and 4

No field names an indexer or a TEE provider. OutLayer context, if built, has its own interface outside the coin (ADR 0007), so a new indexer or a new TEE provider changes nothing here.
